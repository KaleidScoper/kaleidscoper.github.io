# 08 蓝队、检测与应急响应

> 本章解决的问题：**攻击发生的时候，你能不能看见？看见之后，你能不能讲清楚发生了什么、怎么止住、怎么恢复？**

> 蓝队不是"防守方的红队"，也不是"看告警的运维"。它是一门关于**数据、假设、证据和时间线**的工程学科。

---

## 一、蓝队的四个层次

| 层次 | 问题 | 典型工作 | 产出 |
|---|---|---|---|
| 监控（Monitor） | 有没有异常？ | 日志接入、告警、值班 | 告警、ticket |
| 检测工程（Detect） | 为什么这个告警可信？ | 写规则、调优、ATT&CK 映射 | Sigma/YARA/Suricata 规则 |
| 威胁狩猎（Hunt） | 没告警的地方有没有鬼？ | 假设驱动搜索、数据分析 | 狩猎报告、新规则 |
| 应急响应（Respond） | 已经中招了怎么办？ | 遏制、取证、恢复、复盘 | 应急报告、改进项 |

一个成熟的蓝队，四个层次都要有；只会看告警的人，在真实事件里会很快迷路。

## 二、框架：用同一套语言说话

### MITRE ATT&CK

- 按战术（Tactic）组织攻击行为：初始访问、执行、持久化、提权、防御规避、凭据访问、发现、横向移动、收集、命令与控制、外泄、影响。
- 每个技术有编号（如 T1059 命令与脚本解释器、T1003 OS 凭据转储）。
- 用途：检测覆盖度评估、狩猎假设、报告映射、红蓝对抗复盘。
- 注意：ATT&CK 是**行为知识库**，不是检测规则库；截至 2026 年已迭代到 v20，防御侧引入了 Detection Strategies/Analytics，学习时以官网当前版本为准。
- 官网：<https://attack.mitre.org/>

### 其他框架

- **Cyber Kill Chain**：侦察 → 武器化 → 投递 → 利用 → 安装 → C2 → 目标达成。适合讲叙事，不适合细粒度检测。
- **Diamond Model**：对手、能力、基础设施、受害者四要素。适合威胁情报关联。
- **NIST CSF 2.0**：Govern/Identify/Protect/Detect/Respond/Recover。适合管理层和体系建设。
- **NIST SP 800-61 Rev. 3**（2025）：事件响应建议，强调与风险管理融合。适合写应急流程。
- **D3FEND**：防御技术知识库，和 ATT&CK 对应。适合设计控制。

## 三、遥测：没有数据就没有检测

### Windows

- Security 日志：4624 登录、4625 失败、4634 注销、4648 显式凭据、4672 特权登录、4688 进程创建、4720 创建用户、4728 加入全局组、4768/4769 Kerberos。
- Sysmon：进程创建（1）、网络连接（3）、文件创建（11）、注册表（12/13/14）、DNS（22）、映像加载（7）、管道（17/18）。
- PowerShell：4103/4104 脚本块日志、模块日志。
- EDR：进程树、命令行、父进程、哈希、签名、网络。

### Linux

- `auditd`：execve、open、connect、setuid、用户/组变更。
- `journald`/syslog：sshd、sudo、cron、systemd。
- `bash_history`（不可靠，可被清除）。
- eBPF：`bpftrace`、Tetragon、Falco。
- 文件完整性：AIDE、auditd watch。

### 网络

- Zeek：conn、dns、http、ssl、files、notice。
- Suricata：IDS 告警、协议日志、文件提取。
- NetFlow/IPFIX：流量基线、横向移动、外联。
- DNS 日志：DGA、隧道、异常查询。
- 代理/WAF：URL、UA、响应码、拦截。

### 云与身份

- AWS CloudTrail、GuardDuty、VPC Flow Logs。
- Azure Activity Log、Entra ID 登录日志、Defender for Cloud。
- 阿里云 ActionTrail、云安全中心。
- Kubernetes audit log、Falco、服务网格遥测。

**原则**：先问"我要检测什么行为"，再问"哪个数据源能看到"，最后才接日志。不要为了"全量"而接一堆永远不看的日志。

## 四、SIEM 与查询

- **Splunk**：SPL（`index=... | stats count by ...`）。
- **Elastic**：KQL/EQL；Kibana。
- **Microsoft Sentinel**：KQL。
- **Wazuh**：开源 HIDS/SIEM，规则和 decoder。
- **Security Onion**：Zeek/Suricata/Elastic/Stenographer 一体化。

**SIEM 的四个问题**：

1. 数据是否完整、时间是否准确（NTP）？
2. 字段是否规范化（用户、主机、IP、进程、哈希）？
3. 关联是否有意义（不是把 10 条低危告警拼成 1 条高危）？
4. 告警是否有人负责、有 runbook、有 SLA？

**练习**：

1. 用 Splunk Free 或 Elastic 接入 Sysmon + Windows Security 日志。
2. 写 10 条 SPL/KQL 查询：登录失败暴破、异常进程、DNS 异常、PowerShell 编码命令、服务创建。
3. 给每条查询写"误报来源"和"调优方法"。

## 五、检测工程：从假设到规则

### 生命周期

1. **假设**：攻击者会怎么做？对应 ATT&CK 技术是什么？
2. **数据**：哪个日志能看见？字段是什么？
3. **逻辑**：什么条件算异常？阈值/基线/白名单？
4. **实现**：Sigma/YARA/Suricata/SIEM 查询。
5. **测试**：用 Atomic Red Team/Caldera/手工模拟触发。
6. **调优**：误报、漏报、性能。
7. **文档**：目的、范围、误报、处置、参考。
8. **退役**：过时/低价值的规则要删。

### Sigma

- 厂商无关的检测规则格式，可转换为 Splunk/Elastic/Sentinel 等查询。
- 结构：`title`、`id`、`status`、`description`、`references`、`author`、`logsource`、`detection`、`falsepositives`、`level`、`tags`。
- 官网：<https://sigmahq.io/>。

### YARA

- 基于文本/二进制模式匹配，适合恶意样本分类。
- 规则：`meta`、`strings`、`condition`。
- 注意：YARA 不是行为检测；容易被混淆/加壳绕过。

### 测试

- **Atomic Red Team**：按 ATT&CK 技术提供原子测试。
- **Caldera**：自动化 adversary emulation。
- **手工模拟**：在隔离环境执行命令，观察日志。
- **回放**：用历史日志/PCAP 回放，验证规则。

### 交付

- [ ] 20 条 Sigma 规则，覆盖至少 8 个 ATT&CK 战术。
- [ ] 每条规则有测试记录：触发命令、日志、告警截图、误报分析。
- [ ] 1 份检测覆盖度矩阵：ATT&CK 技术 × 数据源 × 规则 × 状态。

## 六、威胁狩猎

### 假设驱动

不要"随便搜搜"。每次狩猎从一个假设开始：

> "如果攻击者用 PsExec 横向移动，我应该能在 Sysmon 事件 1 中看到 `PSEXESVC` 服务创建，并在事件 3 中看到 445 连接。"

### 流程

1. 选一个 ATT&CK 技术/对手组织/近期事件。
2. 写假设和预期遥测。
3. 查数据：时间范围、主机范围、字段。
4. 分析：基线、异常、关联。
5. 结论：确认/排除/需要更多数据。
6. 产出：狩猎报告 + 新规则/数据源需求。

### 资源

- MITRE ATT&CK、Center for Threat-Informed Defense。
- SigmaHQ、Atomic Red Team。
- 公开事件报告（Mandiant、CrowdStrike、Microsoft、Unit 42、奇安信等）。
- 狩猎报告模板（SANS、Roberts/Brown）。

## 七、应急响应与取证

### 生命周期（NIST SP 800-61r3 的思路）

1. **准备**：预案、联系人、工具、权限、演练。
2. **检测与分析**：确认事件、定级、范围、影响。
3. **遏制**：隔离主机、禁用账号、封 IP、断网（注意取证优先）。
4. **根除**：清除恶意代码、补漏洞、重置凭据。
5. **恢复**：恢复服务、监控、验证。
6. **复盘**：时间线、根因、改进项、报告。

### 取证原则

- **先取证，后操作**：能镜像先镜像，能导出先导出。
- **保持证据链**：谁、何时、从哪、怎么获取、哈希。
- ** volatile 数据优先**：内存、进程、网络连接、登录会话。
- **时间线**：统一时区（UTC），记录来源。
- **不污染**：用只读工具、写保护、干净介质。

### 常见 artifact

| 平台 |  artifact |
|---|---|
| Windows | 事件日志、Sysmon、Prefetch、Amcache、Shimcache、MFT、USN、注册表、LNK、计划任务、服务 |
| Linux | `auth.log`、`syslog`、`auditd`、`bash_history`、`cron`、`systemd`、`/proc`、`ss`、包管理日志 |
| 网络 | PCAP、Zeek/Suricata 日志、DNS、代理、防火墙 |
| 云 | CloudTrail/Activity Log、登录日志、对象存储访问日志、K8s audit |
| 内存 | 进程、网络连接、注入代码、凭据、加密密钥 |

### 工具

- **Volatility3**：内存取证。
- **KAPE**：批量收集 artifact。
- **Velociraptor**：端点取证/狩猎。
- **Autopsy / Sleuth Kit**：磁盘取证。
- **Plaso / Timesketch**：时间线。
- **Eric Zimmerman 工具**：Windows 取证。
- **CyberChef**：解码/转换。
- **REMnux / FLARE VM**：恶意样本分析。

### 报告结构

1. 执行摘要（管理层）。
2. 事件时间线。
3. 影响范围与数据。
4. 根因分析。
5. 处置措施。
6. 证据与 IOC。
7. 改进建议。
8. 附录（日志、哈希、命令）。

## 八、恶意样本 triage（与 07 章衔接）

- 静态：哈希、文件类型、字符串、导入表、签名、加壳。
- 动态：进程、文件、注册表、网络、API。
- 行为映射：ATT&CK 技术。
- IOC：域名/IP/哈希/注册表/互斥体。
- 检测：YARA/Sigma/EDR 规则。
- 报告：样本、行为、影响、处置。

**安全**：只在隔离环境；不运行未知样本；不上传敏感数据。

## 九、指标：蓝队如何证明自己有用

- **MTTD**（平均检测时间）、**MTTA**（平均响应时间）、**MTTR**（平均恢复时间）。
- 告警量、误报率、真实阳性率、重复告警率。
- 检测覆盖率（ATT&CK 技术/数据源）。
- 狩猎次数、产出规则数、规则命中率。
- 演练结果：红队被发现的平均时间、遏制时间。
- 不要用"告警数量"当 KPI；那只会制造噪声。
