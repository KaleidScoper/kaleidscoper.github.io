# 12 项目、作品集与求职

> 本章解决的问题：**"我学过"没人信，"我做过且能证明"才有人信。**

安全行业招聘有一个残酷的现实：简历上写"熟悉 OWASP Top 10"的人很多，能拿出"我测过什么、怎么测、发现了什么、怎么修"的人很少。作品集就是把你和"只会背概念"的人区分开的东西。

---

## 一、作品集的三条原则

1. **可复现**：别人按你的 README 能跑起来、能复现实验。
2. **有思考**：不只是截图和命令，要写"为什么这么做、失败过什么、怎么取舍"。
3. **合规**：不泄露客户/学校/公司数据；不发布未修复漏洞细节；不放恶意样本；不写真实目标。

**禁止**：
- 把靶场 writeup 说成"某企业渗透测试"。
- 把别人的报告改名字当成自己的。
- 公开客户数据、内网 IP、账号密码。
- 发布可直接武器化的 0day/恶意代码。

## 二、12 个项目（按阶段）

### 阶段 1：地基

#### 项目 1：家庭/实验网络拓扑与威胁模型

- **目标**：画出你的实验网，标出资产、信任边界、数据流。
- **交付**：拓扑图、资产清单、5 个威胁、对应控制、1 页说明。
- **验收**：外行能看懂图；每个威胁都有具体控制，不是"加强安全意识"。
- **时间**：3～5 天。

#### 项目 2：Linux 加固基线 + 自动化脚本

- **目标**：按 CIS Benchmark 选 20 项，写检查/加固脚本。
- **交付**：脚本、前后对比、回滚方案、例外说明。
- **验收**：在干净 VM 上可重复执行；不会把自己锁在外面；有测试。
- **时间**：1～2 周。

#### 项目 3：抓包分析报告

- **目标**：抓一次完整 HTTPS/HTTP 交互，解释每一层。
- **交付**：pcap（脱敏）、时序图、字段解释、异常分析。
- **验收**：能指出 DNS/TCP/TLS/HTTP 的关键字段；能解释一次重传或延迟。
- **时间**：3～5 天。

### 阶段 2：核心

#### 项目 4：漏洞 Web 应用 + 安全重写

- **目标**：写一个含 3 种漏洞（SQLi/XSS/越权）的小应用，再修复。
- **交付**：漏洞版本、修复版本、diff、测试、报告。
- **验收**：每个漏洞有 PoC、根因、修复、回归测试；修复后无法复现。
- **时间**：2～3 周。

#### 项目 5：Web 应用测试报告

- **目标**：对一个本地靶场（Juice Shop/DVWA）做完整测试。
- **交付**：执行摘要、范围、方法、发现（含严重性）、证据、修复建议、附录。
- **验收**：至少 8 个发现，其中 2 个需要业务逻辑/权限组合；报告能让开发直接修。
- **时间**：2～3 周。

#### 项目 6：AD 攻击与防御实验

- **目标**：搭一个小型 AD，模拟一条从普通用户到域管的路径，再写检测。
- **交付**：拓扑、攻击链（ATT&CK 映射）、日志、检测规则、加固方案。
- **验收**：能解释 Kerberos 票据流转；能说清每个阶段看什么日志。
- **时间**：3～4 周。

### 阶段 3：专精

#### 项目 7：检测规则库（Sigma + 测试）

- **目标**：写 20 条 Sigma 规则，覆盖 8 个战术。
- **交付**：规则、测试记录、误报分析、覆盖度矩阵、部署说明。
- **验收**：每条规则有真实日志触发；误报有解释；能在 Splunk/Elastic 转换。
- **时间**：3～4 周。

#### 项目 8：应急响应演练报告

- **目标**：模拟一次勒索/钓鱼/Web 入侵事件，从告警到复盘。
- **交付**：时间线、证据、遏制/根除/恢复、根因、改进项、管理层摘要。
- **验收**：时间线可追；证据有哈希；改进项有 owner 和期限。
- **时间**：2～3 周。

#### 项目 9：二进制漏洞分析/writeup 集

- **目标**：20 道 pwn 或 10 个 crackme + 1 个真实 CVE 分析。
- **交付**：每篇：保护机制、漏洞点、利用思路、失败尝试、修复建议。
- **验收**：能复现；能解释每一步为什么；不是照抄 writeup。
- **时间**：4～6 周。

#### 项目 10：Fuzzing 报告

- **目标**：对一个开源解析器 fuzz 24～72 小时。
- **交付**：harness、语料、覆盖率、crash 去重、根因、修复建议。
- **验收**：至少 1 个可复现 crash；能判断是否可利用；报告可读。
- **时间**：2～4 周。

### 阶段 4：工程化

#### 项目 11：安全 CI/CD + K8s 加固

- **目标**：一条带 SAST/依赖扫描/镜像签名/准入控制的流水线。
- **交付**：代码、流水线、策略、威胁模型、运行截图、回滚方案。
- **验收**：故意引入漏洞能被拦住；签名验证失败能阻止部署；有文档。
- **时间**：3～4 周。

#### 项目 12：Capstone：迷你企业红蓝对抗

- **目标**：把前面所有项目串起来，做一次完整的红蓝对抗。
- **交付**：红队报告、蓝队报告、管理层摘要、修复计划、复盘。
- **验收**：至少 3 条攻击路径；至少 2 条被检测；有 5 条以上改进项并落地。
- **时间**：6～8 周。

## 三、每个项目的 README 模板

```markdown
# 项目名

## 1. 目标与非目标
## 2. 环境与版本
## 3. 架构/拓扑
## 4. 方法（为什么这么做）
## 5. 关键发现/实现
## 6. 失败与取舍
## 7. 安全与合规说明
## 8. 复现步骤
## 9. 测试与验证
## 10. 已知限制
## 11. 参考
```

> "失败与取舍"是最能体现水平的部分。只写成功的人，通常没真正做过。

## 四、报告写作

### 4.1 渗透测试报告结构

1. **封面**：客户、项目、日期、版本、密级。
2. **执行摘要**：给管理层的 1 页；风险等级、关键发现、建议。
3. **范围与方法**：目标、时间、限制、工具、标准。
4. **发现列表**：按严重性排序；编号、标题、位置、影响。
5. **详细发现**：复现步骤、证据、影响、修复建议、参考。
6. **附录**：工具输出、账号、时间线、术语。

### 4.2 写作原则

- **先结论，后过程**：管理层只看前两页。
- **可复现**：步骤、请求、响应、截图；不依赖"你应该知道"。
- **讲影响**：不要只说"存在 XSS"，要说"可窃取会话，导致账号接管"。
- **给方案**：具体到代码/配置，不要只说"加强过滤"。
- **分级**：CVSS + 业务影响；不要为了显得严重而夸大。
- **脱敏**：客户名、IP、账号、数据。

### 4.3 常见扣分项

- 只有工具输出，没有手工验证。
- 把"低危"写成"高危"。
- 没有复现步骤。
- 修复建议不可执行。
- 泄露敏感数据。
- 报告里有拼写/格式错误。

## 五、GitHub 与博客

### GitHub

- 每个项目一个 repo，README 完整。
- 提交历史清晰：小步提交，消息说明"做了什么、为什么"。
- 不放密钥、样本、客户数据。
- 用 `.gitignore` 排除 `*.pcap`、`*.env`、`samples/`。
- 给项目加 LICENSE（MIT/Apache-2.0/GPL，按需）。
- 用 GitHub Actions 跑测试/扫描，展示工程能力。

### 博客

- 写"过程"而不是"结论"：怎么发现问题、怎么排除、学到什么。
- 每篇有可复现步骤、环境、参考。
- 漏洞披露遵守 responsible disclosure；未修复的不写细节。
- 中文/英文都可以；英文能扩大读者，但不要机翻。

### 作品集页面

一页式：

```markdown
# 名字
安全工程师 / 方向

## 我能做什么
- 3 句话，配 3 个项目链接

## 项目
- 项目名：一句话 + 链接 + 关键结果

## 写作
- 3 篇最好的文章

## 证书/教育（可选）
## 联系方式
```

## 六、简历

### 一页原则

- 姓名、联系方式、GitHub/博客。
- 一句话定位："应用安全/蓝队/云安全方向，2 年实验室与项目经验"。
- 技能：只写能经得起追问的；分"熟练/了解"。
- 项目：3～5 个，每个 2～3 行，写"做了什么 + 结果 + 技术"。
- 证书：与目标岗位相关的 1～2 个。
- 教育：非科班写相关课程/自学路径。

### 项目 bullet 公式

> **动作 + 对象 + 方法 + 结果**

例子：

- "搭建含 AD/Web/K8s 的隔离实验室，用 Atomic Red Team 验证 20 条 Sigma 规则，将模拟攻击的检测覆盖率从 40% 提升到 75%。"
- "对一个开源 Flask 应用做代码审计，发现 3 个越权/注入问题，提交 2 个 PR 并被合并。"

### 不要写

- "精通"（除非你真的能扛住 30 分钟追问）。
- 不存在的公司/项目。
- 把靶场写成"某企业"。
- 与岗位无关的堆砌。

## 七、求职渠道

- **校招/实习**：学校就业网、公司官网、牛客、实习僧。
- **社招**：BOSS 直聘、拉勾、猎聘、LinkedIn。
- **安全社区**：先知、FreeBuf、看雪、CTF 群、OWASP 分会。
- **内推**：前同事、学长学姐、CTF 队友、开源社区。
- **甲方/乙方**：乙方（安全服务/咨询）项目多、成长快；甲方（互联网/金融/国企）更稳定、更重工程/合规。
- **岗位关键词**：渗透测试、红队、应用安全、安全研发、安全运营、应急响应、云安全、合规咨询、漏洞研究。

**策略**：先投 10 家练手，再投目标公司；每次面试后记录问题，补缺口。

## 八、面试准备

### 8.1 技术题（示例）

**网络**
- TCP 三次握手/四次挥手；为什么 TIME_WAIT？
- HTTPS 握手过程；证书链如何验证？
- DNS 解析过程；DNS 劫持/隧道如何检测？

**系统**
- Linux 提权常见路径；如何排查 SUID？
- Windows 登录过程；Kerberos 票据类型？
- 容器逃逸的常见原因？

**Web**
- SQLi/XSS/CSRF/SSRF 的原理与防御。
- 水平/垂直越权如何测试？
- JWT 的常见漏洞？
- 反序列化漏洞的利用条件？

**密码学**
- 对称/公钥/哈希/MAC 的区别。
- 为什么密码不能用 SHA-256 存？
- TLS 1.3 的改进？

**蓝队**
- 如何检测 PsExec/Kerberoasting/黄金票据？
- 应急响应的步骤；先取证还是先关机？
- 如何写一条 Sigma 规则？

**云**
- 共享责任模型；IAM 最小权限；K8s RBAC。
- SSRF 打云 metadata 如何防御？

**场景**
- "给你一个登录接口，怎么测？"
- "发现一台主机外联 C2，怎么处置？"
- "业务要求明天上线，但扫描出高危漏洞，怎么办？"

### 8.2 回答框架

- **定义**：一句话说清概念。
- **原理**：为什么会有这个问题。
- **例子**：一个具体场景/命令/日志。
- **防御**：怎么修/怎么检测。
- **边界**：什么情况下不适用。

> 不会的题，说"我没做过，但我会这样查/这样验证"，比瞎编好。

### 8.3 行为题

- 你最有成就感的安全项目？
- 你和开发/运维冲突过吗？怎么解决？
- 你犯过什么错？怎么补救？
- 你怎么保持学习？
- 你为什么做安全？

用 STAR（情境、任务、行动、结果），结果尽量量化。

### 8.4 反问

- 团队的安全职责如何划分？
- 新人前 3 个月的目标是什么？
- 团队最近一次应急/演练是什么？
- 安全在研发流程中的位置？
- 培训/认证/会议支持？

## 九、第一份工作前 90 天

- 第 1～2 周：搞清资产、系统、流程、联系人；读历史报告/预案。
- 第 3～4 周：接手一个小任务（漏洞验证、日志接入、规则调优）。
- 第 2 个月：独立完成一次小范围评估/应急；写文档。
- 第 3 个月：提出一个改进项并落地；复盘。
- 不要一上来就"改革"；先理解为什么现状是这样。

## 十、长期发展

- **技术路线**：高级工程师 → 专家/架构师 → 首席安全科学家。
- **管理路线**：安全经理 → 安全总监 → CISO。
- **研究路线**：漏洞研究、恶意代码、密码学、AI 安全。
- **创业/咨询**：安全服务、产品、培训。
- 不管哪条路，**写作、表达、商业理解**都是瓶颈。

## 十一、自测

1. 你的作品集里，哪一个项目能经得起 30 分钟追问？
2. 你的报告能让开发直接修吗？能让老板看懂吗？
3. 你的 GitHub 有 README、测试、License 吗？
4. 你的简历有没有"精通"但答不上来的词？
5. 你能用 3 分钟讲清你最好的项目吗？
6. 你有没有持续输出（博客/演讲/开源）？
7. 你最近一次失败的项目是什么？学到了什么？
8. 你知道目标岗位的 JD 里，哪些要求你还没有证据吗？
