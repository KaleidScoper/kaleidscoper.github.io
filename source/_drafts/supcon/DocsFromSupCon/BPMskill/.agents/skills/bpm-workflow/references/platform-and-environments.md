# BPM 系统、环境与平台基础

## 3. 系统与环境基础

BPM 是中控集团（SUPCON）内部的业务过程管理平台，部署在多个 VPS 环境中。底层为自研低代码平台 BAP（Orchid BAP），使用 OSGi bundle、Maven 和 `bundle-settings` 构建，已知版本示例为 `4.60.50.00`。

开发和沟通时通常用内网 IP 地址的最后一节来简称环境，例如 `10.30.5.213` 可称为“213”或“213 环境”。有可能产生歧义时，不使用简称。

部分 `module.xml` 将模块环境标成 200，但实际归属不同。判断模块归属时参考下表，并核对模块和目标环境。

访问服务器或数据库以本次任务明确的环境和操作范围为准；执行已授权技能流程所必需的访问，不重复索取授权。

BPM 登录时需选择“中控集团”或“中控技术”账套，账套与登录用户名分别核对。代码复核、保存和模块发布必须在页面确认当前账套精确为“中控集团”后执行，使用对应环境的获准账号，不能凭用户名是否为 `admin` 推断账套。中控技术账套用于单据执行和测试，不在其中进行代码、视图、数据库定义等管理操作、模块发布或上载。

自动执行单据遇到具体阻塞，且证据表明业务数据修正确有必要时，可通过独立数据库连接按[业务数据修正规程](../../../../docs/待整合skills/auto-execute-document/references/database-repair.md)执行。用户要求执行该技能覆盖其规定的小范围修正：默认同一目标业务对象、直接 DML 累计不超过10行，执行前保存原值、修复方案和恢复 SQL，核对事务与实际影响行数，再通过正常页面继续流程。不得直接改流程状态、生效时间、引擎、待办、审批历史、权限或数据库结构。

仿真环境在不同需求类型中的用途不同：

1. **开发需求**：开发先在测试环境完成冒烟验证，测试团队再在测试环境执行正式测试。正式测试通过后，由测试团队负责将代码包部署到仿真环境并进行回归验证。开发不负责常规的仿真部署和回归操作；仿真回归出现问题时，开发再协助复现、定位并解决。
2. **BUG 修复需求**：开发在开始分析和修改前，通常先到仿真环境执行原问题的复现步骤，记录操作路径、输入数据、期望结果、实际结果、时间点、模块版本以及可获取的页面、日志和接口证据。后续修复仍需经过开发环境修改、测试环境验证和测试团队的仿真回归。
3. **操作边界**：在仿真环境复现 BUG 时，应使用获准的账号、测试数据和操作路径，避免执行与复现无关或可能破坏环境数据的操作。无法安全复现时，应先说明风险并请求明确的复现安排。

实际操作前，核对本次需求的环境、模块和访问地址。

### 3.4 重启 Java（BPM 应用）

重启 BPM 的 Java 进程不等于重启整台 VPS。大多数环境的重启入口是 BAP 目录 `bin/` 下的 `bpm_restart.sh`，必须先进入脚本所在目录再执行：

```bash
cd /export/group/bap-server/bin
sh bpm_restart.sh cq
```

- 唯一有效参数是 `cq`；脚本内的 `Usage: bash $0 {restart}` 提示与实际分支不一致。
- 脚本只处理 Java：按 `bap-workspace` 匹配进程后 `kill -9`，再执行同目录 `startup.sh -clean -debug 9005`（`startup.sh` 转调 `dmk.sh start`），不含整机重启命令。
- 脚本以相对路径 `./startup.sh` 启动，不能在其他目录直接执行 `sh /export/group/bap-server/bin/bpm_restart.sh cq`：那样只会停掉 Java，启动失败且输出被重定向，BPM 会停留在停止状态。
- 200 开发环境的 BAP_HOME 是 `/export/BAP38/bap-server`，重启脚本为 `/export/BAP38/bap-server/bin/bpm_restart.sh`，同样要先 `cd` 到该 `bin/`；该文件没有执行权限，只能用 `sh` 调用。
- 部分环境另有 `/root/restartbpm.sh`、`/root/script/restartbpm.sh` 等遗留脚本（注释为每天凌晨重启 BPM），没有 cron 调度，不作为常规入口。
- 2026-10-28 核查时，仿真环境各节点账号认证失败、51 只能经堡垒机访问，均未取得重启路径；执行前先确认，不能直接套用上述命令。

## 4. 平台结构与代码定位方法

BPM 各环境的模块代码通常位于服务器的 `/export/group/bap-server/bap-workspace/generate/` 下，几乎没有例外。查找具体模块时，先以该路径为定位线索。例外情况须报告。

115 开发环境的 CRM 模块目录为 `/export/group/bap-server/bap-workspace/generate/techCRM_1.0.0/`。整文件上传时，交付包 `java/` 下的 `core/`、`service/` 路径直接对应此模块目录；`java/` 本身不属于服务器目标路径。

### 4.1 组织层级

BPM 模块通常按以下层级组织：

1. **模块**：平台代码库和交付物的基本单位。下载代码包中的 `module.xml` 集中记录模块、实体、视图、菜单和工作流等元数据。
2. **实体**：模块内的业务对象，实体编码通常带模块前缀，并可能配置单据头部信息。
3. **模型**：实体下的数据模型，对应传统开发中的数据库表。
4. **视图**：对应传统开发中的前端页面，可能使用 FTL 模板，位于 `views/<模块>/<实体>/<模型>/` 一类目录中；一般以当前模块实际路径为准。
5. **脚本**：流程脚本，通常位于 `scripts/<模块>_<实体>/`。
6. **服务实现类**：通常与模型对应，并以 `ServiceImpl` 结尾；实际类名必须通过源码确认。

实体列表在 VPS 前端分页显示，注意提醒我在第一页看不到完整列表，并不代表实体不存在。实体信息可能以“实体编码、实体名称、单据头部信息”三个信息一组展示，查找时需要我翻页并核对完整信息。

单据头部信息通常是单号前缀，不一定等同于业务上的正式编号。某些正式编号只有在单据生效后才生成；遇到未生效单据无法按正式编号检索时，应从项目名称、客户名称或其他稳定业务字段入手，并通过当前模块代码和页面确认具体规则。

### 4.2 实体配置、菜单、视图与工作流

“实体配置”列出模块；进入模块后可查看实体，并执行模块级的代码下载、上载和发布。进入实体配置后，可查看自定义代码、关联工作流、菜单和数据库定义。若现场入口不同，说明实际路径。

菜单主要是导航和功能入口，不宜直接等同于页面；视图通常更接近完整的前端页面，而不是普通前端小组件。菜单、视图和工作流不是简单的逐级包含关系：工作流部署元数据可同时关联 `entityCode` 和 `menuCode`，流程节点还可通过 `doURL`、`viewName` 和 `viewCode` 指向具体页面。

`contract2_1.0.0` 下载包的 `service/src/main/resources/META-INF/bap/module.xml` 包含 `<deployments>`／`<deployment>`，其中记录 `processKey`、`menuCode`、`entityCode` 和 JPDL `<processXml>`。

分析工作流时，应区分以下四层：

1. **可视化流程配置**：由人类开发者在实体配置页面的工作流编辑器中查看和修改。
2. **代码包中的序列化定义**：下载快照中可能以 `module.xml` 内嵌 `<processXml>` 的形式保存流程定义，便于阅读流程结构并审查前后差异。
3. **业务代码与引擎的交互**：Java／FTL 通过 `ProcessService`、`InstanceService`、`TaskService`、`TransitionService`、`deploymentId`、`pendingId` 和 `WorkFlowVar` 等服务或上下文使用工作流，不是在业务类中重新实现流程图。
4. **目标环境运行态**：实时部署 ID、流程实例、当前待办、节点状态和变量值属于工作流引擎的运行态，不能仅从静态代码包完整确认。

工作流写入 `module.xml` 的具体时机尚未验证；需要判断时，对比相关操作前后的下载包。

### 4.3 “自定义代码”入口、左侧树和源码保留区域

根据用户 2026-10-10 补充的实际操作方式，进入模块 M 下任意实体 N 的编辑页，点击边栏“自定义代码”，均打开 M 的整个模块代码编辑器。入口所在实体不限制可见代码范围。“自定义代码”并非某一个源码编辑区域的名称，不应与 Java 文件中的 `CUSTOM CODE START(...)` / `CUSTOM CODE END` 保留区域混为一谈；后者用于在平台重新生成时保留业务代码。

编辑器左侧的三模式文件树正式称为“左侧树”：

| 模式 | 文件范围及根目录 | 修改单中的路径写法示例 |
| --- | --- | --- |
| `all` | 模块全部有效文件；根目录为模块根目录 | `service/src/main/java/com/supcon/orchid/trainMana2/services/impl/TrainMana2ColseprojMServiceImpl.java` |
| `service` | `service/src/main/java/com/supcon/orchid/<模块名称>/` 下的有效文件 | `services/impl/TrainMana2ColseprojMServiceImpl.java` |
| `view` | `service/src/main/resources/views/<模块名称>/` 下的有效文件 | `closeProj/colseprojM/closeProjEdit.ftl`；视图配置使用设计器，自定义代码区可在代码编辑器修改 |

搜索框只搜索当前模式范围内的文件，不搜索文件夹。关键字支持 `*`：`MES*.java` 搜索以 MES 开头且名称包含 .java 的文件，另有 `*.java`、`*areaListRef*fastquery*datatable.ftl`、`*Basic*ServiceImpl.java` 等用法。输入关键字后自动搜索，可以使用上下键再按回车选中记录。

现场代码修改单同时给出模块、入口实体、左侧树模式、该模式内相对文件路径、类名／文件名、文件内 Ctrl+F 稳定锚点和具体修改动作；本地绝对路径只能用作证据链接，不能代替平台路径。需要整方法替换时给出完整可粘贴方法，尽可能保持无关逻辑和原有格式。

视图自定义代码修改单按上述代码定位要求给出路径、锚点和修改内容，并说明“保存并发布”操作。视图配置修改单从元数据核对页签编码／编号、名称和表格，明确模型字段编码、字段类型、长度、显示类型、只读／必填等属性；页面显示顺序不是设计器编号。

### 4.4 低代码修改与新建自建文件

低代码修改：人类明确要求 Agent 执行时，在本地准备 Java 或视图自定义代码变更，仅将匹配的 `CUSTOM CODE` 区域同步到服务器，再通过内置浏览器进入模块 Web 代码编辑器逐文件复核和保存。人工也可直接在 Web 编辑器修改。视图配置通过 BPM 可视化视图设计器修改；FTL 的自定义代码区允许在视图代码编辑器修改，保留生成区；工作流在实体配置页面的可视化工作流编辑器修改。

新建自建文件：对完全新建且不参与平台重新生成的代码文件，可按明确的开发要求在本地编写并整文件上传至开发环境（如 SFTP）；是否需要平台保存取决于文件的实际生成机制。修改 BPM 生成文件时仍走上述低代码自定义区同步和 Web 保存流程。

### 4.5 代码保存、视图保存并发布与模块普通发布

后端代码编辑器使用“保存”按钮；视图编辑器的“保存并发布”也显示在视图的代码编辑器界面。这两种保存操作均不等同于模块“普通发布”。

| 视图保存并发布（含视图代码编辑器） | 后端代码保存 | 模块普通发布 | 结果 |
| --- | --- | --- | --- |
| 按下 | — | — | 当前模块已发布且在线时，视图变更立即生效。 |
| — | 按下 | — | 当前模块已发布且在线时，运行行为不变；后端代码变更在下一次模块发布后生效。 |
| — | — | 按下 | 自上次模块发布以来的所有变更生效，模块提供的服务（菜单）立即可用。 |

## 5. 常见平台能力

### 5.1 公开接口与会话

`/public/` 是免登录接口的常见路径，可直接通过 HTTP 联调；部分服务通过 `custSetSession` 按员工编码模拟登录。联调时检查目标接口权限和响应。

### 5.2 接口日志（BPM 原生日志）

BPM 原生接口日志用于忠实保存一次实际接口调用的请求与响应，便于在“接口数据日志”页面核对接口交互。请求报文保存实际发送的内容，返回报文保存实际收到的内容；解密、解析后的数据和业务处理摘要不能替代原始报文。人员选择、兜底判断、未清类型重建等内部处理过程，不应仅因希望在 BPM 页面可查就另记成接口日志。

在实际接口调用处直接使用平台已有服务；仅转发参数的通用包装方法没有必要。接口编码使用当前接口已确认并登记的固定编码，不按内部业务分支另造编码，也不把某个需求的编码套用到其他接口：

```java
intfLogService.saveIntfLog(接口编码, 时间, 主数据ID, 成功标志, 重试次数, 返回值摘要, 请求报文, 返回报文)
```

模块代码中通常注入 `com.supcon.orchid.BasicInfo.services.BasicInfoIntfLogService`，变量名多为 `intfLogService`。

可在 BPM 页面搜索“接口数据日志”，再按接口编码筛选。排查问题时应核对实际发生的接口调用及对应请求、响应，不根据内部处理摘要推断接口已经调用成功。

### 5.3 系统配置

系统配置采用 KV 形式，常见读取方式为：

```java
sysConfigHeadService.getSysConfigCode("键名")
```

已知键名示例包括 `productPriceConfig_url`、`productPriceConfig_cturl`、`S2Bsubflow`、`BasicInfo.syncS2B` 和 `companyid_xxx`。这些仅用于帮助检索，实际含义和值必须在目标环境中核实。

### 5.4 系统编码

业务字典中的系统编码在平台“系统编码”中维护，并随模块打包为 `service/src/main/resources/META-INF/bap/systemcode.xml`。文件以 `<bapSystemCode>` 为根，每套字典对应一个 `<systementity code="..." moduleCode="...">`，其下每个子项对应一个 `<systemcode id="..." code="..." value="..." fullPathName="...">`；代码和页面按完整编码标识（如 `basicData2_custpic_contact_department`）取值。在低代码平台新增或修改系统编码会使该文件产生差异，入库时按 GitLab 同步规则提交到该模块对应的 GitLab 仓库，不能只提交代码 diff。

### 5.5 服务器运行日志与 BPM 原生日志

`log.info`、`log.error` 等 SLF4J 日志（例如 `log.info("任意信息" + textVariable);`）写入环境所在服务器的运行日志，用于内部处理、诊断信息和异常排查，不会进入“接口数据日志”页面。它们与 5.2 的 BPM 原生接口日志用途不同；接口日志需要保存的真实请求、响应，不能用服务器日志或业务摘要代替。

接口编码必须已在平台登记对应接口定义，未登记时 `intfLogService.saveIntfLog(...)` 会报“接口编码无对应接口”，并可能抛出 `BAPException`。不能把写入服务器摘要视为 BPM 接口日志已保存。当前平台日志服务使用独立事务（`REQUIRES_NEW`），接口日志存在也不代表调用方的业务事务最终提交成功；需分别核对接口响应与业务落库结果。
