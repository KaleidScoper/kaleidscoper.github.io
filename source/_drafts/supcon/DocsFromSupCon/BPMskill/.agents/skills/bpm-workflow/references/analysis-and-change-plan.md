# BPM 需求分析与现场修改单

## 6. 标准分析与交付流程

### 6.1 分析需求和确认归属

1. 先区分完整开发或 BUG 修复需求与独立执行单据、仅同步保存等阶段任务；阶段任务按本次目标执行，不自动扩展到整个开发交付链。需要分析修改时，再判断开发、BUG 修复或混合需求，并分别列出适用的分析、验证和环境使用要求。
2. 对于 BUG 修复需求，通常先在仿真环境复现原问题并收集证据，再分析代码、工作流和其他相关配置并提出修改方案。复现失败时，说明已执行的步骤、实际结果、环境版本和仍缺少的信息。
3. 阅读需求原文，列出明确目标、输入、输出、业务边界和验收条件。
4. 检查 `module.xml`、实体、模型、视图、脚本、服务实现、i18n 和现有调用方，确认当前项目是否承载目标功能；涉及工作流时，还要检查 `<deployments>`／`<processXml>`、`processKey`、`menuCode`、`entityCode` 和节点关联的 `doURL`／`viewCode`。
5. 对接口、页面、字段中文名、实体归属和流程节点等概念，优先用源码、i18n、设备页面、接口日志和实际数据相互印证。静态 `module.xml` 只能证明下载快照中的序列化定义，目标环境当前流程版本、运行实例、待办和变量仍需现场证据确认。
6. 将需求原文、用户说明和工作区文档与当前源码及现场证据交叉校验。发现描述性认知冲突时，不得为迎合既有提示词而忽略证据；应说明冲突、采用的判断依据和不确定性，并判断是否需要提醒用户更新提示词体系。
7. 如果当前项目很可能不匹配需求，停止推演修改方案，明确给出证据、可能的正确模块和待确认项。

### 6.2 制定最小修改方案

1. 先判断本次需求需要修改代码、视图、实体／模型配置、工作流，还是其中多项的组合，不能默认所有 BPM 开发都只涉及 Java／FTL。
2. 只设计需求必需的修改，优先复用现有方法、服务、视图、流程节点和脚本，以 diff 最小为第一要务，不对需求涉及范围之外的代码做换行、空白或其他格式规范化。本次需求以外的旧代码格式缺陷，以及其他不阻塞本次功能实现的内容，不顺手修复、重排或清理；保留无关逻辑和原有格式，不得移除其他人的原有注释。现场修改单和整文件替换交付同样适用。
3. 除非需求确实要求，不新增接口、不改 `core` 层、不扩大业务语义。
4. Java 改动放入合适的 `CUSTOM CODE START(...)` / `CUSTOM CODE END` 区域，避免平台重新生成时被覆盖。服务实现中的函数区常见标记为 `CUSTOM CODE START(serviceimpl,functions,...)`，但必须以目标文件的实际标记为准。“自定义代码”编辑器可打开模块所有有效文件，不代表其中每一行都是平台生成保留区。
5. 工作流改动以实体配置页面的可视化工作流编辑器为标准操作入口。应最小化节点、流转线、分支条件、人员分配、脚本和关联视图的变化，并核对相关代码或脚本依赖；不得默认以手工修改 `module.xml` 中的 `<processXml>` 代替可视化编辑。
6. 先核对代码和工作流的实际约束，再设计测试用例。例如，如果代码硬性限制某个数组只能有一条数据，就不能把多条数据用例当成正常路径；如果流程对新实例和已在途实例采用不同定义，也必须分别明确验证范围。
7. 明确区分“外部系统调用 BPM 的接口”和“BPM 内部调用其他服务的接口”，日志名称和验收口径以实际 `intfLog` 编码与调用链为准。
8. 本次需求新增或修改的 Java 代码块均须就近注明 `//年月日 edit by zhangyingzhong（张瀛中）for 需求`，将“年月日”替换为实际修改日期（`yyyyMMdd`），将“需求”替换为实际需求名称。删除逻辑时，在保留下来的相关代码附近注明本次删除；不为留痕保留无效或重复实现。整文件替换也只标注本次改动，不得覆盖或移除他人原有注释。

### 6.3 输出现场修改单

常规低代码需求按执行顺序说明修改：Java 后端代码定位到生成文件的自定义区及 Web 代码编辑器，视图配置定位到可视化视图设计器，视图自定义代码定位到代码编辑器中的对应自定义区，工作流定位到可视化工作流编辑器。人类明确要求 Agent 执行代码修改或同步时，按交付流程准备本地变更、同步自定义区并完成 Web 复核保存；需要人工执行的部分仍给出现场修改单。每一步直接写入口、目标和动作；同一事实只写一次，只有影响执行的差异或不确定项才单列。

视图自定义代码修改单按下述代码修改单要求给出路径、锚点和修改内容，并说明“保存并发布”操作。视图配置修改单给出设计器中的实际页签编码／编号与名称、表格、增列／改列、模型字段编码、字段类型及长度、显示类型、只读／必填等属性，并说明涉及的编辑页或查看页配置。

需求涉及完全新建且不参与平台重新生成的自建文件时，给出本地文件、开发环境目标路径、整文件上传方式及生效和验证步骤。修改 BPM 生成文件时，仍提供自定义区及 Web 编辑器定位，按低代码流程保存。

常规低代码需求的代码修改单每处改动至少包括：

- 模块、实体、模型和代码视图；
- “自定义代码”左侧树模式、该模式内准确相对路径、完整本地证据路径和类名／文件名；文件树模式及搜索规则按 `platform-and-environments.md` 第 4.3 节；
- 当前文件中的行号；如果行号可能随平台生成变化，同时给出唯一或稳定的上下文锚点；
- 应删除、替换或新增的完整代码；人工调整缩进或拼接成本较高时，提供可直接粘贴的整个方法，保留无关逻辑与格式，尽可能缩小 diff；
- 选择该位置和实现方式的依据；
- 可能受影响的调用方、数据、页面和流程节点；
- 发布前后的核对项。

工作流修改单每处改动至少包括：

- 模块、实体、工作流名称和 `processKey`；能取得时同时记录当前版本、`lastModify` 或其他可区分流程定义的标识；
- 在实体配置页面进入可视化工作流编辑器的路径；
- 要修改的节点名称／编码、流转线名称／编码、分支条件或其他稳定锚点；
- 当前配置与目标配置，包括新增、删除或调整的节点、流转线、条件、人员分配、脚本、`doURL`、`viewCode` 和生效设置；
- 关联的 Java 服务、流程脚本、视图、菜单、权限、数据和外部接口，以及这些关联是否需要同步修改；
- 对新发起流程和已在途流程的预期影响；平台版本行为尚未验证时，应明确标为待确认；
- 保存、普通发布、代码包下载、`module.xml` 目标差异审查以及开发／测试环境验证要求。

如果代码和工作流需要配套修改，修改单还应说明两类修改的执行顺序、接口或变量契约，以及只完成其中一类修改时会出现的中间态风险。
