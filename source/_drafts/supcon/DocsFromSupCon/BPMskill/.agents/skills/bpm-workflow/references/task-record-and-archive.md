# BPM 任务记录与归档

## 1. 活跃任务记录

1. BPM 开发或 BUG 修复任务开始后，使用 `docs/active/任务记录模板.md` 在 `docs/active/` 下建立该任务的记录；已有记录时续写原文件，不重复创建。
2. 任务记录用于保存需求原文、需求类型、模块归属、环境、代码与工作流证据、现场修改单、交付进度、验证证据、未确认事项，以及任务中发现的提示词系统冲突和更新建议。
3. 只记录已经确认的事实。尚未提供、尚未执行或无法验证的内容标为“待确认”“未执行”或“未验证”，不得补写为已完成。
4. 模块判断必须保留证据。如果 `BPM_Modules/` 为空、现有模块明显不正确或代码与工作流证据不足，应在记录中写明异议、候选模块和待确认项。

## 2. 更新时机

在以下信息发生变化时更新同一份活跃任务记录：

- 需求类型、目标、业务边界或验收条件；
- 候选模块、确认模块、模块路径或项目归属证据；
- 开发、测试、仿真环境及其本次职责；
- 代码现场修改单及其目标文件、行号、锚点和影响范围，或工作流现场修改单及其目标实体、`processKey`、节点／流转线锚点和影响范围；
- 设备代码和／或工作流修改、普通发布、代码包下载和 GitLab 同步状态；
- 合并请求、Jenkins 构建、测试环境部署、开发冒烟、提交测试和仿真回归状态；
- 用户说明或提示词体系与源码、现场配置、日志、接口响应、页面行为或其他关键事实之间的冲突，以及建议更新的规则文件和位置；
- 新增证据、失败结果、风险或未确认事项。

## 3. 完成与归档

1. 用户确认本次任务满足完成条件后，读取活跃任务记录和当前任务中的证据，在 `docs/archive/` 下生成任务记录。
2. 归档记录应反映实际完成范围，不得把未执行的测试、未发生的部署或未确认的结果写成已经完成。
3. 独立执行单据、仅同步保存等阶段任务按本次指定目标判断完成，不自动套用整个开发交付链。对于完整开发需求，开发阶段的交付完成条件仍以 `AGENTS.md` 中“设备代码和／或工作流修改与普通发布、代码包下载、目标改动入库、合并请求、Jenkins 构建、测试环境上传、开发冒烟、提交测试”的完整链路为准。
4. 对于 BUG 修复需求，归档记录还应保留仿真环境修复前复现证据、修复后的测试环境验证以及测试团队仿真回归的实际状态。
5. 归档记录至少应保留 `references/final-response.md` 所列且适用于本任务的内容，以及仍未确认的事项。
