# BPM 工作流

按照工作区根目录 `AGENTS.md` 中的工作约束、证据校验、冲突处理、职责边界和模块判断规则开展工作。根据当前任务所处阶段，只读取下面与该阶段直接相关的 reference；任务跨越多个阶段时，再依次读取相应文件。

## 参考资料路由

- 需要确认环境职责、BPM 平台结构、“自定义代码”入口、左侧树 all/service/view 模式与文件搜索路径、源码保留区域、公开接口、接口日志（BPM 原生日志）、系统配置或系统编码时，读取 [平台与环境基础](references/platform-and-environments.md)。
- 需要分析需求、区分开发需求与 BUG 修复、判断模块归属、判断是否涉及工作流变更、制定最小修改方案或输出现场修改单时，读取 [需求分析与现场修改单](references/analysis-and-change-plan.md)。
- 需要处理设备代码或工作流修改后的交付链、GitLab 精确同步、Jenkins、测试环境、仿真环境或接口联调验证时，读取 [交付与验证流程](references/delivery-and-validation.md)。
- 需要组织阶段性或最终答复时，读取 [最终答复要求](references/final-response.md)。
- 需要建立、续写或归档任务记录时，读取 [任务记录与归档](references/task-record-and-archive.md)，并使用 `docs/active/任务记录模板.md`。

## 执行要求

1. 先确认或质疑当前模块，再分析修改位置；不能因为 `BPM_Modules/` 中存在某个模块目录就默认它属于当前需求。
2. 如果 `BPM_Modules/` 为空、模块明显不正确或证据不足，停止推演具体修改，说明依据、候选模块和仍需确认的信息。
3. 任务事实和阶段变化应写入 `docs/active/` 下对应记录；未确认的信息必须保留为“待确认”。
4. 常规低代码需求中，人类明确要求 Agent 执行代码修改或同步时，在本地准备本次变更，仅同步生成文件的 `CUSTOM CODE` 区域，再通过内置浏览器逐文件复核和保存；这是 Web 低代码流程的一部分，具体步骤见 `references/delivery-and-validation.md`。人工也可直接在 Web 代码编辑器修改。视图配置和工作流使用各自的可视化设计器；视图自定义代码区允许在代码编辑器修改并“保存并发布”，保留 FTL 生成区。整文件直接上传主要用于完全新建且不参与平台重新生成的自建文件，目标路径、生效与验证按本次需求确定。
5. 按当前任务需要使用浏览器，无需另行请求浏览器许可。自定义代码同步后的界面复核与保存是必需步骤；模块发布仍须用户本次明确要求。
6. BPM 模块 GitLab 仓库的提交与推送只在用户明确要求后执行，并且只处理本次需求产生的目标改动；这里不涉及本工作区 `D:\CodexWorkSpace\BPM` 自身的 Git 库。目标改动不限于代码 diff：人类开发者在低代码平台完成的配置变更也可能在下载包中形成额外差异；例如新增或修改系统编码时，应把 `systemcode.xml` 中对应的编码变更一并提交到该模块的 GitLab 仓库，使合并后上载到任何环境都不需要重新配置系统编码。详细核对要求见 `references/delivery-and-validation.md`。
7. 把用户说明和提示词中的 BPM 描述作为需要由当前证据校验的认知，不因其写入规则文件就忽略与源码、现场配置、日志、接口响应、页面行为或其他关键事实的冲突；用户明确给出的授权、公司流程、职责分工和操作边界仍必须遵守。
8. 发现提示词体系可能过时或有误时，在当前阶段答复和活跃任务记录中写明冲突、证据、影响以及建议更新的文件和位置。未经用户明确要求，不自行修改提示词体系。
9. 修改单和最终答复按读者执行顺序写，直接说明当前已知的入口、操作和结果；同一事实只说一次，只列会影响修改或验证的不确定事项。发现现场差异时，说明差异及其影响，不在每条已知事实后重复添加泛泛的保留话。
10. 一般禁止未经用户明确许可备份任何文件，包括本地文件、服务器文件以及以快照或校验副本名义保留的完整文件。修改、同步、保存或发布授权不自动包含备份授权；默认在内存中读取、比较和校验，不落地原文件副本，也不为可选备份阻塞已获准的操作。只有用户明确许可时才按许可范围备份。原子替换所需的临时文件只用于完成本次写入，替换后即被消耗，并在操作结束时清理，不作为备份保留。
