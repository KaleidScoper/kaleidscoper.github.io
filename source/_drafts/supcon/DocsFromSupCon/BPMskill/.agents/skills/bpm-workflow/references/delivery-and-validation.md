# BPM 交付与验证流程

### 6.4 设备修改与普通发布

按本次任务范围选取本节及后续交付步骤；独立执行单据、仅同步保存等阶段任务不自动套用整个开发交付链。人类明确要求 Agent 执行代码修改或同步时，按[自定义代码同步流程](../../../../docs/待整合skills/bap-remote-custom-code-sync-zh/SKILL.md)处理 BPM 生成文件中的 Java 或视图自定义代码，主要步骤如下；人工也可直接在 Web 代码编辑器修改。视图配置在 BPM 可视化视图设计器修改，视图自定义代码区允许在代码编辑器修改，保留 FTL 生成区；工作流在实体配置页面的可视化工作流编辑器修改。多类修改同时存在时，核对代码、流程脚本、变量和节点视图之间的契约。

1. 在本地准备本次变更，核对目标环境、模块、文件及匹配的 `CUSTOM CODE START/END` 标记。先预检区外差异、变更规模和计划哈希；区外存在内容差异或目标不唯一时停止。
2. 携带已核对的预检哈希，仅同步匹配自定义区中的本次改动，保留其余服务器原文及换行；使用临时文件原子替换，并核对 UTF-8、乱码和写入后的内容。一般禁止未经用户明确许可备份任何文件；修改、同步、保存或发布授权不包含备份授权。默认只在内存中读取原文用于比较、校验和失败恢复，不落地原文件副本。原子替换临时文件只承载本次写入内容，操作结束时清理；只有用户明确许可备份后才启用同步脚本的 `--backup-authorized`。
3. 使用内置浏览器，在已确认的“中控集团”账套进入模块 Web 代码编辑器，逐文件比较本次修改：后端代码点击“保存”，视图代码点击“保存并发布”，并确认持久化结果。不得以 SSH 回读或平台保存接口替代浏览器逐文件复核与保存。
4. 用户本次明确要求模块发布时，再核对账套及模块，在装载状态监控中选择目标模块的“普通”列执行发布并确认结果；未要求发布时，报告同步保存结果及尚未普通发布的状态。

整文件直接上传主要用于完全新建且不参与平台重新生成的自建代码文件。按明确的开发要求在本地编写并上传至开发环境（如 SFTP），上传后的生效、入库与验证流程按本次需求确定。

上传自建文件前，核实目标模块目录及目标文件是否已存在；需要覆盖已有自建文件时，先与交付基线比对，查清差异，不覆盖来源不明的现场改动。用户明确要求直接覆盖时，上传到对应路径，不擅自创建服务器备份或暂存目录。仅上传清单中的源码，上传后逐文件核对 SHA-256；文件一致表示上传完成，不表示已普通发布或通过业务验证。

对普通发布会重新生成的 Java 文件（如平台生成的 Service、ServiceImpl、Action），仅写服务器文件不会更新平台保存的自定义代码，发布时本次修改可能被还原，必须完成上述 Web 复核和保存。无此生成机制的自建文件不要求一律触发平台保存。后端代码保存仅持久化内容，变更在下一次模块发布后生效；视图代码编辑器的“保存并发布”在模块已发布且在线时使视图变更立即生效。后端代码保存、视图“保存并发布”和模块“普通发布”的区别见[平台与环境基础](platform-and-environments.md#45-代码保存视图保存并发布与模块普通发布)。

修改工作流前，应记录当前工作流名称、`processKey`、可取得的版本或 `lastModify`、目标节点与流转线、关键分支条件、人员分配、脚本及节点页面关联，必要时保留流程图截图，作为修改和回退对照。完成平台要求的保存动作后，按本次发布授权执行该模块的“普通发布”。仅保存后端代码或工作流但未完成普通发布时，不得将改动报告为已经生效。

模块普通发布后立即进行与修改类型匹配的最小烟雾验证。已发布在线模块的视图“保存并发布”后，视图变更立即生效，应直接核对相关页面；完整开发交付仍按后续交付链执行。代码修改可调用目标接口、检查对应接口日志或打开相关页面；工作流修改至少应确认目标流程可以按预期入口发起或继续处理，并核对首个受影响节点、流转条件、办理人和打开页面。完整流程验证仍应在测试环境按用例执行。

### 6.5 下载代码包并同步 GitLab

本节操作对象是各 BPM 模块对应的远程 GitLab 仓库，不是本工作区 `D:\CodexWorkSpace\BPM` 自身的 Git 库。

**模块与 GitLab 仓库对应（已确认的模块）：**

| 模块中文名 | 模块标识 | GitLab 仓库 |
| --- | --- | --- |
| 项目流程管理2 | `trainMana2_1.0.0` / `trainMana2` | `git@gitlab.ops.supcon.com:bpm/trainMana2.git` |
| CRM | `techCRM_1.0.0` / `techCRM` | `git@gitlab.ops.supcon.com:bpm/techCRM.git` |
| 客户供应商管理 | `basicData_1.0` / `basicData` | `git@gitlab.ops.supcon.com:bpm/basicData.git` |
| 客户供应商管理2 | `basicData2_1.0.0` / `basicData2` | `git@gitlab.ops.supcon.com:bpm/basicData2.git` |
| 销售合同管理二 | `contract2_1.0.0` / `contract2` | `git@gitlab.ops.supcon.com:bpm/contract2.git` |
| 工程服务外包管理 | `EngManage_1.0.0` / `EngManage` | `git@gitlab.ops.supcon.com:bpm/EngManage.git` |
| 工程业务管理 | `projOrder_1.0.0` / `projOrder` | `git@gitlab.ops.supcon.com:bpm/projOrder.git` |

先按上表定位当前模块的候选仓库；未列出的模块不得按名称猜测，必须结合下载包 `module.xml` 中的模块标识和 `git remote -v` 核实。实际远程地址仍以目标仓库的 `git remote -v` 为准，本表只用于选择候选仓库和防止串库。

1. 从完成普通发布的 BPM 开发环境下载该模块代码包。涉及工作流修改时，必须使用修改并发布后的新下载包，不得沿用修改前的 `module.xml` 快照。
2. 先按本节“模块与 GitLab 仓库对应”表定位候选仓库，再用 `git remote -v` 核实实际远程仓库，不要依赖历史地址或仅凭模块名猜仓库。
3. 获取最新 `origin/main`，从 `main` 创建本次临时分支。
4. BPM 设备代码与仓库 `main` 可能存在大量历史漂移；本地工作区也可能包含来源不明的未提交变更。只把本次需求涉及的目标代码、视图、脚本或工作流序列化差异转移到临时分支。
5. 目标改动不限于代码 diff。人类开发者在 BPM 低代码平台完成的配置变更也可能在下载包中形成额外文件差异；例如新增或修改系统编码后，`service/src/main/resources/META-INF/bap/systemcode.xml` 会新增、修改或删除对应的 `<systementity>`／`<systemcode>` 项。该文件属于本次交付，应随目标改动一并提交到该模块对应的 GitLab 仓库，使合并后上载到任何环境都不需要重新配置系统编码；不能把它当作无关生成物排除，也不能只提交 Java／FTL 等代码 diff；即使本次没有代码 diff，只有系统编码变更，也应提交该文件。该文件通常是单行大文件，行级 diff 可能覆盖整行，应按 `systementity` 的 `code`、`moduleCode` 和 `systemcode` 的 `id`、`code`、`value`、`fullPathName` 核对本次增删改。提交时以 `main` 中的该文件为基线，只合入本次需求相关的编码变更并保留其他既有编码定义，不得把下载包中与本次无关的历史漂移或他人配置差异整文件带入。
6. 涉及工作流修改时，应优先比较修改前后的下载代码包，定位 `module.xml` 中目标实体对应的 `<deployment>`／`<processXml>` 差异，并核对 `processKey`、`menuCode`、`entityCode`、节点、流转线、条件、人员分配、脚本及 `doURL`／`viewCode`。不得把同一巨大 `module.xml` 中与目标流程无关的其他生成差异一并视为本次改动；如果新下载包中未出现预期流程差异，应停止手工补写并核实平台实际在哪个操作阶段输出该定义。
7. 提交前逐文件审查完整 diff，确认本次代码及系统编码等平台配置差异均已包含，并确保没有设备全量差异、无关生成物或他人改动混入，然后再 `commit` 和 `push`。
8. 向 `main` 创建合并请求，并按团队流程处理评审；确认系统编码等非代码差异保留在合并请求中，不被当作无关生成物剔除。是否必须先合并再构建，应以 Jenkins 作业配置和团队要求为准。

Windows 遇到超长文件名导致 `checkout` 或 `worktree` 失败时，可先执行：

```powershell
git config core.longpaths true
```

必要时在基于 `origin/main` 的临时 `worktree` 中制作精确补丁。不要为了消除差异而直接覆盖当前设备快照，也不要提交所有未提交文件。

### 6.6 Jenkins 构建、测试环境部署与提交测试

1. 提出合并请求后，在 Jenkins 触发当前模块对应的构建任务；先核实作业要求的分支或提交，不假定它一定构建已合并的 `main`。
2. 核对 Jenkins 使用的仓库、分支／提交和模块，取得本次构建产物。
3. 将构建得到的代码包上传到指定 BPM 测试环境。
4. 开发在测试环境执行核心冒烟用例，确认本次改动已部署且关键路径可用，并保留请求与响应、接口日志、页面结果和必要页签等截图证据。
5. 涉及工作流修改时，开发冒烟至少覆盖正确流程定义被发起、首个受影响节点、关键流转条件、办理人或候选人、节点打开的页面、相关流程脚本以及预期结束或生效行为。是否影响修改前已经在途的流程实例必须单独核实，不得用新实例验证结果替代该结论。
6. 将版本、构建信息、部署环境、冒烟步骤、实际结果、已知边界和截图清单一并提交测试团队。
7. 测试团队在测试环境执行正式测试。开发应配合解释修改范围和已知边界，但不应把开发冒烟当成测试团队的正式测试结果。

Jenkins 构建成功只代表构建完成，不等于业务验收通过。必须确认测试环境实际运行的是本次产物，并验证用户可观察的业务结果。

### 6.7 仿真环境回归与问题协助

1. 对于开发需求，测试环境正式测试通过后，由测试团队将已经验证的代码包部署到仿真环境并执行回归验证。
2. 开发不需要主动承担常规仿真部署或重复执行测试团队的完整回归；只有仿真回归出现问题时，开发才介入协助。
3. 开发介入时，先核对仿真环境运行的模块版本、代码包、工作流、配置、数据条件、复现步骤和错误时间，再比较测试环境与仿真环境的差异，判断问题来自代码、工作流、部署、配置、数据还是环境依赖。
4. 如果确认需要继续修改代码或工作流，应重新走开发环境修改与普通发布、目标改动入库、Jenkins 构建、测试环境验证和仿真回归流程，不要直接在仿真环境修改代码或工作流。
5. 对于 BUG 修复需求，仿真环境既是修复前通常使用的原问题复现环境，也是测试团队在测试环境正式验证通过后的回归环境。修复前后的现象、版本和证据应能对应比较。

## 7. 接口联调与验证规则

### 7.1 接口联调方式

接口可按以下形式联调：

```bash
curl -i -X POST "http://<设备IP>:8087/<接口路径>" \
  -H "Content-Type: application/json;charset=UTF-8" \
  --data-binary "@请求文件.json"
```

请求文件应保存为 UTF-8。JSON 中 `\/` 与 `/` 等价。返回结构必须以实际 action 和响应为准：有的接口直接平层返回，有的会包裹一层 `result`，不能想当然地统一解析。

### 7.2 通用验证顺序

验证应遵循以下顺序：

1. 确认请求已到达目标接口并记录正确的入口日志。
2. 检查被自动调用的后续接口日志，确认完整调用链和数据传递。
3. 打开对应单据或业务页面，验证用户实际看到的结果。
4. 覆盖成功路径、代码明确支持的边界路径和失败路径。
5. 记录无法覆盖或明确不支持的行为，不要等到测试失败后再补充说明。

工作流变更除遵循上述通用顺序外，还应对照修改前流程确认实际启用的 `processKey`／版本、发起入口、每个受影响节点与流转线、分支条件、办理人、节点页面、流程脚本和结束／生效行为。新发起实例与修改前已在途实例应分别记录验证结论；无法确认平台对在途实例采用何种流程定义时，明确列为待确认项。

### 7.3 按需求类型选择验证环境

1. **开发需求**：开发环境用于修改和普通发布；测试环境先由开发执行冒烟，再由测试团队执行正式测试；仿真环境由测试团队部署并进行近生产回归。开发仅在仿真回归出现问题时协助处理。
2. **BUG 修复需求**：通常先在仿真环境复现原问题并保留修复前证据，再进入代码、工作流及其他相关配置的分析和修改；修复产物在测试环境经过开发冒烟和测试团队正式测试后，由测试团队部署到仿真环境回归，并与修复前证据对照。
3. 无论在哪个环境验证，都要记录环境 IP 或无歧义名称、模块版本、代码包或提交、测试数据、操作时间和实际结果，避免把不同环境或不同版本的现象混为一谈。

与需求方或测试团队沟通时，先给出可以直接执行的页面路径、输入框、查询条件、按钮和页签步骤；术语必须与当前页面、i18n 和代码一致。
