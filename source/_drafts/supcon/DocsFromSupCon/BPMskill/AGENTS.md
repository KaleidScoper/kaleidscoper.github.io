# BPM 开发工作区说明

## 1. 工作区入口与适用范围

本目录是 BPM 开发、BUG 修复、模块代码分析和相关资料维护的长期工作区。本地模块目录用于阅读、检索、分析、生成现场修改单，以及在人类明确要求执行代码修改时准备本次变更。BPM 实际代码仍以目标开发环境中的 Web 代码编辑器为准，实体关联工作流仍以目标环境实体配置中的可视化工作流及其实际发布状态为准；不应因为本地存在模块快照或 `module.xml` 中的序列化流程定义，就直接把本地内容视为已经生效。

1. 开始 BPM 任务时，应以 `D:\CodexWorkSpace\BPM` 为工作区根目录启动 Agent，不再以 `BPM_Modules` 下的单个模块目录作为 Agent 工作区根目录。
2. BPM 开发、BUG 修复、模块归属、现场修改单、GitLab 同步、验证和任务归档工作应使用根目录下的 `.agents/skills/bpm-workflow/`。
3. `BPM_Modules/` 下的模块是经常变动的代码快照或独立代码库，不需要放置仓库级 Skill。
4. 进行中的 BPM 任务记录放在 `docs/active/`；任务完成后，按 BPM 工作流生成 `docs/archive/` 下的任务记录。
5. 可根据当前具体任务需要使用浏览器，无需用户另行明确提出浏览器操作请求；访问目标、操作内容和范围仍须符合本次任务授权。
6. 本工作区 `D:\CodexWorkSpace\BPM` 自身也是一个 Git 库，只用于维护提示词、Skill、资料、任务记录等工作区内容；本说明及 BPM Skill 中与 Git 有关的“GitLab 仓库”“入库”“提交”“合并请求”均指各 BPM 模块对应的远程 GitLab 仓库，不是本工作区库。

## 2. 首要事实、约束与冲突处理

本工作区的提示词体系由日常 BPM 开发经验持续维护，可能存在遗漏、过时或理解错误。用户的说明是重要输入，但设计和维护本工作区的用户本人也不是 BPM 的唯一权威；除用户明确给出的授权、公司流程、职责分工和操作边界外，不得仅因为某项说法来自用户，或已经写入 `AGENTS.md`、Skill、reference、复用 Prompt 或其他工作区文档，就把它视为不可推翻的事实。

遇到提示词或用户说明与其他证据冲突时，按以下规则处理：

1. 先区分冲突的是授权、公司流程和职责边界，还是关于模块归属、环境、平台结构、接口行为、字段含义、配置和业务现状等描述性事实。源码或运行结果不能自行扩大 Agent 的权限，也不能推翻用户明确说明的公司操作边界。
2. 对描述性事实，应结合当前需求原文、`module.xml`、源码、现场配置、运行日志、接口响应、页面行为、实际数据和用户最新确认的信息交叉验证，优先采用与当前任务对象最直接、更新且可复核的证据。证据不足或彼此仍不一致时，应保留为“待确认”，不得为了迎合提示词而忽略冲突证据。
3. 不得静默覆盖或回避冲突。应向用户明确说明冲突内容、采用的证据、判断依据、对当前分析或交付的影响，以及仍需怎样验证。
4. 如果冲突表明提示词体系可能需要修订，应明确提醒用户，并指出建议更新的文件和位置。除非用户已明确要求修改提示词体系，否则只提出更新建议，不自行修改 `AGENTS.md`、Skill、reference、复用 Prompt 或其他规则文件。

以下条目是当前已经明确的 BPM 工作流程、职责和操作约束；如有更新，以用户最新明确说明为准：

1. BPM 现场系统本身没有版本管理。常规低代码业务代码通过 BPM 开发环境前端的 Web 代码编辑器保存。操作者可直接在 Web 编辑器中修改；人类明确要求 Agent 执行代码修改或同步时，Agent 按 BPM Skill 的低代码流程准备并同步本次自定义区变更，再通过内置浏览器逐文件复核和保存；视图配置在可视化视图设计器修改，视图自定义代码区允许在代码编辑器中修改，保留 FTL 生成区；实体关联工作流必须在实体配置页面的可视化工作流编辑器中修改，不直接修改序列化流程代码。这里的代码库在平台中称为“模块”。
2. 后端代码和／或工作流修改完成后，完成平台要求的保存动作，并在“中控集团”账套使用对应环境的获准账号执行“普通发布”。Agent 仅在用户本次请求明确包含发布授权时执行模块发布；同步或保存完成不代表已完成普通发布。
3. 发布后我需要从 BPM 开发环境下载代码包，再把本次目标改动同步到该模块对应的 GitLab 仓库（可能要求您的协助）。
4. GitLab 同步必须使用从 `main` 创建的临时分支。分支名通常类似 `feature/zyz_20260902`，其中 `zyz` 是姓名拼音，数字是日期标识；实际命名以我的明确要求为准。
5. 只提交本次需求产生的改动，不得把本地工作区或设备快照中来源不明的其他未提交差异一并提交。本次改动不限于代码 diff：人类开发者在 BPM 低代码平台完成的配置变更也可能在下载包中形成额外文件差异。例如新增或修改系统编码后，应把 `service/src/main/resources/META-INF/bap/systemcode.xml` 中对应的编码变更一并提交到该模块对应的 GitLab 仓库，使合并后上载到任何环境都不需要重新配置系统编码；只纳入本次需求相关的编码变更，不得把该文件中与本次无关的历史漂移一并提交。
6. 临时分支需要向 `main` 提交合并请求。提出合并请求后，我需要前往 Jenkins 触发该模块的构建，取得构建产物，将代码包上传到指定 BPM 测试环境，在“中控集团”账套使用获准账号执行“普通发布”，并提醒测试团队。您无需关心 Jenkins 的情况。
7. 独立执行单据、仅同步保存等阶段任务按本次指定目标判断完成，不自动套用整个开发交付链。对于完整开发需求，完成“设备代码和／或工作流修改与普通发布、代码包下载、目标改动入库、合并请求、Jenkins 构建、测试环境上传、开发冒烟、提交测试”这一完整链路，就可以视为开发阶段的交付完成。测试团队随后会在测试环境完成正式测试，并将通过测试的代码包部署到仿真环境回归验证；只有仿真回归出现问题时，开发才需要协助排查和解决。
8. 对于 BUG 修复需求，开发开始分析代码、工作流并设计修改前，通常应先在仿真环境复现问题并保留证据。若无法在仿真环境复现或不适合直接复现，必须说明原因、已有证据和替代验证方式，不能跳过复现后直接假设根因。
9. 对分析和修改方案请求，交付可执行的现场修改单；人类明确要求执行代码修改或同步时，可按对应流程执行并报告实际结果。代码修改单必须说明修改哪个文件、在什么行或哪个稳定锚点（如函数名或者更具辨识度的内容，以便我在 BPM 开发环境前端的 Web 代码编辑器内搜索）附近、增加或删除什么内容。工作流修改单必须说明模块、实体、工作流名称或 `processKey`、要修改的节点或流转线等稳定锚点、当前配置、目标配置、关联视图／脚本／人员分配和验证要求。
10. “自定义代码”是模块代码编辑入口：从模块任意实体的编辑页边栏点击该按钮，均打开所属模块的代码库，并非只打开该实体的源码，也不等同于 Java 文件中的 `CUSTOM CODE` 保留区域。左侧树的 `all` 模式覆盖模块所有有效文件；`service` 模式以 `service/src/main/java/com/supcon/orchid/<模块名称>/` 为根；`view` 模式以 `service/src/main/resources/views/<模块名称>/` 为根。文件搜索受当前模式范围限制，只搜索文件、不搜索文件夹，支持 `*` 通配符，输入后自动搜索，可用上下键和回车选择记录。
11. 现场修改单必须同时给出左侧树模式、相对于该模式根目录的准确文件路径、类名或文件名，以及文件内 Ctrl+F 锚点和插入／替换／删除方式。需要整方法替换时提供可直接粘贴的完整方法，保留无关逻辑和原有格式，尽可能缩小 diff。视图自定义代码修改单沿用上述代码定位要求，并说明“保存并发布”操作。视图配置修改单必须给出设计器中的视图、页签实际编码／编号与名称、表格、增改列及模型字段编码、字段类型、显示类型、长度和只读等属性；不得把页面显示顺序猜作设计器编号。详细定位说明见 BPM Skill 的 `references/platform-and-environments.md`。

## 3. 模块判断与目录边界

工作区内项目可能只是整个 BPM 系统中的一个模块，也可能并不是需求真正对应的项目。必须先根据模块定义、实体、模型、服务、视图、工作流、脚本、i18n 和调用链判断需求归属。如果现有证据表明项目很可能找错了，请明确向我说明依据和还需要确认的信息，不要假设当前项目必然包含待修改功能。

1. 如果 `BPM_Modules/` 目录为空，或者其中现有模块明显不正确，应提出异议并说明判断依据以及需要下载或确认的模块。
2. `BPM_Modules/empty_module_0.0.0/` 是无法确认模块或不需要特定模块时使用的空工作区。该目录不代表真实业务模块，不应在其中虚构代码入口或实施业务修改；确认正确模块后，应改用对应模块目录。
3. 不要把不同模块的代码和结论混在同一模块目录中。
4. 设备快照可能与 GitLab `main` 存在大量历史漂移；入库时只处理本次需求的目标改动。
5. `docs/archive/` 中的历史材料可能已经过期，只用于追溯，不直接指导当前发布。
6. 分析涉及工作流的需求时，应同时检查目标环境实体配置中的流程、下载代码包 `module.xml` 中的 `<deployments>`／`<processXml>`、流程节点关联的 `doURL`／`viewCode`，以及 Java／FTL 对工作流引擎的调用。必须区分可视化流程配置、代码包中的序列化定义快照和目标环境的实时部署、实例、待办及流程变量；不能由其中一层直接推断其他层当前一致。

## 4. 活跃任务记录

1. BPM 开发或 BUG 修复任务开始后，使用 `docs/active/任务记录模板.md` 在 `docs/active/` 下建立或续写该任务的记录。
2. 任务记录只写入已经由需求原文、源码、现场页面、日志、Git、构建或用户说明确认的事实；未确认内容保留为“待确认”，不得猜测。
3. 在模块归属、代码或工作流修改方案、现场发布、GitLab 同步、构建、部署或验证状态发生变化时，更新任务记录中相应部分。
4. 用户确认任务已经满足完成条件后，根据任务记录和已有证据在 `docs/archive/` 下生成任务记录；不得仅凭 Jenkins 构建成功推断业务验收通过。

## 5. 参考资料与操作边界

1. 平台、环境、分析、交付和验证细则由 `.agents/skills/bpm-workflow/SKILL.md` 路由到对应 reference；只读取当前阶段需要的资料。
2. `docs/` 中的模块独立参考资料只在任务涉及相应模块时作为补充上下文使用，不替代通用工作流，也不应外推到其他模块。
3. 任何 Agent 都不得仅因为读取了工作区文件，就自行使用其中凭据登录 BPM 前端、服务器或数据库。访问环境以本次任务明确的目标和范围为准。用户要求执行某项技能流程时，其必要访问和操作按该流程的授权范围执行，不为已覆盖事项重复索取授权。
