# BPM 开发工作区

## 1. 工作区用途

本目录是 BPM 开发、BUG 修复、模块代码分析和相关资料维护的长期工作区。开始任务时，应以本目录作为 Agent 工作区根目录，根目录的 `AGENTS.md` 会提供始终有效的工作约束，`.agents/skills/bpm-workflow/` 会按当前任务阶段加载相应流程。首条用户消息使用 `docs/BPM开发复用Prompt.md`，只需将任务占位内容替换为实际需求。

本地模块目录主要用于阅读、检索、分析和生成现场修改单。BPM 实际代码仍以目标开发环境中的 Web 代码编辑器为准，实体关联工作流仍以目标环境实体配置中的可视化工作流及其实际发布状态为准；不应因为本地存在模块快照或 `module.xml` 中的序列化流程定义，就直接把本地内容视为已经生效。

## 3. 推荐使用方法

### 3.1 已知业务模块

1. 以 `D:\CodexWorkSpace\BPM` 作为工作区根目录启动 Agent，不要在 `BPM_Modules/<模块目录>/` 中单独启动。
2. 阅读 `docs/BPM开发复用Prompt.md`，填入实际需求；可以同时说明候选模块为 `BPM_Modules/<模块目录>/`。
3. Agent 仍需根据 `module.xml`、实体、模型、视图、工作流、脚本、服务实现、i18n 和调用方确认模块归属，不因为用户选择了目录就默认项目一定正确。
4. 如果 `docs/` 中存在该模块的独立参考资料，可作为补充证据使用；模块源码、目标环境页面和运行日志仍具有更高的现场验证价值。

### 3.2 无法确认业务模块

1. 仍以 `D:\CodexWorkSpace\BPM` 作为工作区根目录启动 Agent；`BPM_Modules/` 可以为空，也可以仅存在 `empty_module_0.0.0/`。
2. 先依据需求、环境模块清单、接口路径、页面名称、实体、模型、工作流和调用关系判断功能归属，不要假设空模块包含待修改功能。
3. 确认模块后，从对应 BPM 开发环境下载模块代码，放入 `BPM_Modules/<模块目录>/`，再由 Agent 读取该目录继续分析，不需要更换 Agent 工作区根目录。
4. 如果现有证据仍不足以确认模块，应明确列出候选模块和需要人类补充的信息，不在空模块中生成虚构的文件路径、行号、代码修改或工作流配置。

### 3.3 销售合同管理任务

以 BPM 根目录作为 Agent 工作区，使用 `BPM_Modules/contract_1.0.0/` 作为主要代码分析对象，同时按需查阅 `docs/销售合同管理模块参考资料.md`。涉及 S2B 产品型合同接口时，可以使用 `docs/s2b.json` 了解请求结构，但其中的数据只能作为样例，联调前必须替换或核实。

## 4. 使用边界

1. 不要把不同模块的代码和结论混在同一模块目录中。
2. 不要把 `empty_module_0.0.0` 当作真实模块，也不要在其中长期保存某个已确认模块的代码。
3. 设备快照可能与 GitLab `main` 存在大量历史漂移；入库时只处理本次需求的目标改动。
4. `docs/archive/` 中的历史材料可能已经过期，只用于追溯，不直接指导当前发布。
5. 任何 Agent 都不得仅因为读取了本文件，就自行使用环境汇总文档中的凭据登录 BPM 前端、服务器或数据库。需要访问环境时，必须先取得人类对本次访问目标和范围的明确授权。
6. 根目录本地 Git 只管理工作区规则、Skill、Prompt、参考资料和任务记录；`BPM_Modules/` 下的全部模块代码由根目录 `.gitignore` 排除，不纳入工作区版本控制。
7. 浏览器操作不属于本工作区预设的 BPM 标准流程。只有用户在某项具体任务中明确要求时，Agent 才能在该任务授权范围内使用浏览器。
