# 09 云原生、供应链与 AI 安全

> 本章解决的问题：**现代系统不再是一台服务器，而是一条从代码提交到云端运行的供应链。攻击者不需要打穿你的防火墙，只需要在你的依赖、流水线或 IAM 里找到一个信任缺口。**

---

## 一、云安全：先换脑子，再学按钮

### 1.1 共享责任模型

- 云厂商负责"云的安全"：物理设施、虚拟化、托管服务的基础安全。
- 你负责"云中的安全"：身份、配置、数据、应用、网络、日志。
- 边界随服务类型变化：IaaS 你管得多，SaaS 你管得少，但**数据和身份永远是你的责任**。

### 1.2 身份是新的边界

- **IAM**：用户、组、角色、策略、权限边界。
- **STS**：临时凭证；比长期 Access Key 安全。
- **OIDC/联邦身份**：CI/CD 用 OIDC 换取短期云凭证，避免把密钥存进仓库。
- **最小权限**：从 `*:*` 开始是灾难；用 Access Analyzer/策略模拟器收敛。
- **权限提升路径**：`iam:PassRole` + `ec2:RunInstances`、`lambda:UpdateFunctionCode`、`sts:AssumeRole` 链。
- **混淆代理（confused deputy）**：第三方服务被诱导使用自己的权限访问你的资源；用 `ExternalId`、条件键、源账号限制。

### 1.3 网络与数据

- VPC、子网、路由表、安全组、NACL、PrivateLink、VPC Endpoint。
- 对象存储：公开桶、ACL、策略、预签名 URL、跨账号复制。
- 密钥管理：KMS/HSM、密钥轮换、信封加密、密钥策略。
- 日志：CloudTrail/Activity Log、VPC Flow Logs、S3 访问日志、GuardDuty/Defender。
- 备份与不可变性：防勒索、跨区域、对象锁。

### 1.4 云攻击路径（防御视角）

1. 暴露的元数据服务（SSRF → IMDS）→ 临时凭证。
2. 过宽的 CI/CD OIDC 信任 → 冒充仓库 → 云角色。
3. 公开的对象存储 → 数据泄露。
4. 过宽的 `AssumeRole` → 跨账号横向。
5. 容器逃逸 → 节点权限 → 云角色。
6. 日志缺失 → 无法发现/取证。

**实验**：

- 用 AWS Free Tier/Azure 学生账号/阿里云免费额度，建一个最小环境：VPC + 一台 VM + 对象存储 + IAM 角色。
- 故意把桶设为公开，再用 bucket policy 修复；用 CloudTrail 看操作记录。
- 用 `Prowler`/`ScoutSuite`/`CloudSploit` 做一次基线扫描，读报告。

**认证（可选）**：AWS Security Specialty、Azure AZ-500、CCSP。不要为了证书而学，先做项目。

## 二、容器与 Kubernetes

### 2.1 容器不是虚拟机

- 容器 = 命名空间（隔离视图）+ cgroups（资源限制）+ capabilities + seccomp/AppArmor/SELinux + 联合文件系统。
- 共享内核：内核漏洞、逃逸、侧信道是容器安全的底层风险。
- 镜像 = 代码 + 依赖 + 配置 + 历史；镜像层可能泄露密钥。

### 2.2 容器安全清单

- [ ] 使用最小基础镜像（distroless/alpine），减少攻击面。
- [ ] 非 root 运行；只读根文件系统；禁用 privilege escalation。
- [ ] 删除不需要的 capabilities；默认 seccomp/AppArmor。
- [ ] 镜像扫描（Trivy/Grype）；签名（cosign）；固定 digest。
- [ ] 不在镜像里放密钥；用 Secret Manager/CSI driver。
- [ ] 限制网络出口；不要 `--net=host`。
- [ ] 运行时检测（Falco/Tetragon）。

### 2.3 Kubernetes 安全

- **API Server**：认证、授权（RBAC）、准入控制、审计日志。
- **etcd**：加密 at rest、访问控制、备份。
- **Kubelet**：认证/授权、只读端口、证书轮换。
- **RBAC**：最小权限；避免 `cluster-admin`；注意 `create pods` 可挂载 Secret、`exec` 可进容器。
- **NetworkPolicy**：默认拒绝，按需放行。
- **Pod Security Standards**：baseline/restricted；用 PSA 或 Kyverno/OPA 强制。
- **Secret**：base64 不是加密；启用 encryption at rest；外部 Secret Store。
- **供应链**：镜像签名、准入校验（cosign policy controller）、SBOM。
- **多租户**：命名空间隔离不够；需要网络策略、资源配额、准入、节点隔离。

**实验**：

- 用 kind/minikube 建集群，部署一个应用。
- 故意给 ServiceAccount 过宽权限，从 Pod 内访问 API Server，观察能做什么，再收敛 RBAC。
- 用 Kyverno 写 3 条策略：禁止 latest 标签、禁止 privileged、要求资源限制。
- 用 Trivy 扫描镜像，修一个高危漏洞。
- 用 Falco 检测一次容器内 shell 启动。

**认证（可选）**：CKS（Kubernetes Security Specialist）。

## 三、CI/CD 与软件供应链

### 3.1 流水线威胁

- 恶意 PR 修改 CI 配置，窃取密钥。
- 依赖混淆：内部包名被公共仓库抢注。
- Typosquatting：`reqeusts` 之类。
- 被接管的维护者账号发布恶意版本。
- 构建缓存/产物被篡改。
- 过宽的 CI token 可以推送代码/发布包。
- 自托管 runner 被攻陷，横向到生产。

### 3.2 防御

- **最小权限**：CI token 只读、短期、按仓库/环境隔离。
- **OIDC**：用短期云凭证，不存长期密钥。
- **固定依赖**：lockfile、hash 校验、私有 registry、依赖审核。
- **SBOM**：SPDX/CycloneDX，记录组件和版本。
- **签名与验证**：Sigstore/cosign、in-toto、SLSA  provenance。
- **构建隔离**：ephemeral runner、不可变基础设施、分离构建与部署权限。
- **审计**：谁触发了流水线、改了什么、产出了什么。

### 3.3 SLSA 与 SBOM

- **SLSA**：供应链完整性分级框架，关注源码、构建、依赖、产物；分 Build/Source 等 track。
- **SBOM**：软件物料清单；不是"安全证明"，但没有它你无法响应 Log4Shell 这类事件。
- **in-toto**：记录供应链每一步的签名元数据。
- **Sigstore**：`cosign` 签名/验证，`fulcio` 证书，`rekor` 透明日志。

**实验**：

- 用 GitHub Actions 建一条流水线：测试 → SAST（Semgrep）→ 依赖扫描（Trivy/Grype）→ 构建镜像 → cosign 签名 → 部署到 kind。
- 故意提交一个高危依赖，验证门禁能拦住。
- 生成 SBOM，查一个已知漏洞组件。
- 用 OIDC 让 GitHub Actions 扮演云角色，删除长期 Access Key。

## 四、AI 安全

> 这里的 AI 安全指"保护 AI 系统"和"用 AI 辅助安全"，不是"用 AI 攻击人"。所有红队测试必须在授权环境进行。

### 4.1 为什么 AI 系统是新的攻击面

- 输入是自然语言，边界模糊；传统输入校验不够。
- 模型行为不可完全预测；同一输入可能不同输出。
- 工具调用/代理（agent）让模型能执行真实操作。
- 训练数据、模型权重、向量库、插件都是供应链。
- 输出会被下游系统当作代码/HTML/SQL/命令执行。

### 4.2 OWASP Top 10 for LLM Applications 2025

| 编号 | 风险 | 一句话 | 防御要点 |
|---|---|---|---|
| LLM01 | Prompt Injection | 恶意输入改变模型指令 | 隔离指令/数据、最小权限、输出校验、人工确认 |
| LLM02 | Sensitive Information Disclosure | 模型泄露训练数据/上下文/密钥 | 数据分类、脱敏、上下文隔离、输出过滤 |
| LLM03 | Supply Chain | 模型/数据/插件/依赖被污染 | 来源验证、签名、SBOM、模型扫描 |
| LLM04 | Data and Model Poisoning | 训练/微调数据被投毒 | 数据来源、清洗、评估、版本控制 |
| LLM05 | Improper Output Handling | 输出被下游当代码执行 | 输出编码、沙箱、白名单、不要直接 `eval` |
| LLM06 | Excessive Agency | 代理权限过大 | 最小权限、工具白名单、人类审批 |
| LLM07 | System Prompt Leakage | 系统提示词泄露 | 不把秘密放提示词、假设它会泄露 |
| LLM08 | Vector and Embedding Weaknesses | 向量库/嵌入的越权与投毒 | 租户隔离、访问控制、来源校验 |
| LLM09 | Misinformation | 模型编造/误导 | 引用来源、人工复核、不确定性提示 |
| LLM10 | Unbounded Consumption | 资源耗尽/成本攻击 | 限流、配额、超时、预算告警 |

> 官方页面：<https://genai.owasp.org/llm-top-10/>。版本和条目可能更新，执行前以官网为准。

### 4.3 关键概念

- **直接提示注入**：用户输入直接覆盖系统指令。
- **间接提示注入**：恶意内容藏在网页/文档/邮件/代码注释里，被模型读取后执行。
- **越狱（jailbreak）**：绕过模型安全策略；和提示注入不同，但常一起出现。
- **数据外泄**：模型把上下文/系统提示/其他用户数据带出来。
- **工具滥用**：模型调用 shell/HTTP/数据库时，把不可信内容当命令。
- **模型供应链**：`pickle` 反序列化、恶意 Hugging Face 模型、被篡改的依赖。
- **RAG 安全**：知识库投毒、越权检索、嵌入 inversion。
- **Agent 安全**：多步规划、权限累积、环境交互、意外副作用。

### 4.4 防御原则

1. **把模型当不可信组件**：它的输出和用户输入一样不可信。
2. **指令与数据分离**：系统提示、用户输入、检索内容用明确边界；不要指望模型永远遵守。
3. **最小权限**：工具/凭据/数据访问按任务最小化；高风险操作要人类确认。
4. **输出校验**：按下游上下文编码；禁止直接 `eval`/`exec`/SQL 拼接。
5. **沙箱**：代码执行、浏览器、文件系统隔离。
6. **限流与预算**：防资源耗尽和成本攻击。
7. **日志与可观测**：记录输入、输出、工具调用、决策链；注意隐私。
8. **红队**：用提示注入、数据外泄、工具滥用、越权测试集评估。
9. **治理**：模型卡、数据卡、风险评估、上线审批、事件响应。

### 4.5 AI 治理（与第 10 章衔接）

- **NIST AI RMF**：Govern/Map/Measure/Manage。
- **EU AI Act**：按风险分级，2024 年生效，分阶段适用；高风险系统有额外义务。
- **中国**：《生成式人工智能服务管理暂行办法》（2023-08-15 施行）、《人工智能生成合成内容标识办法》（2025-09-01 施行）、《网络安全法》2025 年修改（2026-01-01 施行）增加 AI 安全与促进条款。
- **企业内控**：AI 使用政策、数据分类、供应商评估、模型上线评审、审计日志。

> 法规细节以官方文本为准；本章只做索引，不构成法律意见。

### 4.6 实验

- 用本地开源模型（Ollama/vLLM）搭一个 RAG 应用，故意放入恶意文档，观察间接提示注入。
- 给模型一个"读取文件"的工具，限制目录，测试越权。
- 写一个输出过滤器，阻止模型输出 HTML/脚本，再测试绕过。
- 用 Garak/PyRIT 做一次基线红队扫描（本地/授权）。
- 写一份 LLM 应用威胁模型（STRIDE + OWASP LLM Top 10 映射）。
